# 工作流升级开发计划

状态：P4a 执行内核、P1 固定 CNB 来源逐个下载、P2 分支入口已实现；P1/P2 已由用户实机验收。P4b 运行生命周期已实现，仍需真实窗口验收。P5 已接入本地 stdio MCP 和受限 JS，配有单次运行授权；本地端到端测试已覆盖只读、写入、JS 桥接与取消，真实窗口交互仍需验收。P6 已接入本地 Skill 与 AI 工具循环，并提供公开 Edge 表单读取、填写样板；确定性 JS 样板已在本机实际 Edge 运行通过，AI 样板及真实窗口交互仍需验收。对应 [架构设计](workflow-architecture-redesign.md)与 [P5 技术验证](workflow-execution-extension-spike.md)。每阶段只修改相关模块，不做全库格式化或顺手重构。

## 1. 实施原则与依赖

- 先验证并建立 v2 执行内核及 v1 兼容层，再交付远端模板与分支入口；v1 文件、快捷键、预览、运行日志与现有 Git 语义必须继续可用。
- 模板目录是全局资源；工作流运行态和来源分支属于 `RepoTabState`。运行始终绑定一个仓库标签页，不因切仓库、切模式、刷新列表而迁移。
- 新增网络操作使用现有代理及凭据策略；所有 Git/IO/MCP/JS 长任务走调度器与事件路由。P5 的隔离验证结果见技术验证文档；正式接入前继续确认宿主桥接和运行时边界。
- 每个阶段都更新 `docs/workflows.md` 的已交付部分。架构设计中的未完成目标不能写成用户已可使用的功能。

执行顺序为 P0 → P4a → P1 → P2 → P4b → P5 → P6。P5 的独立技术验证已在锁定依赖外完成；项目锁定的 Kit 0.6.4 没有 Shell，JS 执行采用独立后台引擎方向，正式接入仍需验证宿主桥接与客户端 release 构建。

当前交付范围：P4a 提供 `invoke` 步骤、内置 `git.*` 动作和可注册的宿主动作接口；现有 v1 步骤仍沿用原执行路径。P1 在工作流页提供“下载模板”弹框，浏览固定 CNB 目录后逐个下载到普通模板目录，不覆盖同名文件；旧版 `remote-cnb` 文件只导入一次，模板列表不再重复扫描。P2 在分支右键菜单列出已加载模板，点击后进入运行页并带入来源分支，仍需手动运行。P1/P2 已由用户实机验收。

P4b 增加运行令牌、步骤边界取消和扩展动作取消入口；进度、完成及失败事件校验标签页、仓库、运行 ID 与模板代际。失败或取消后尽力刷新仓库快照，避免已执行步骤造成的状态停留在旧快照。真实窗口中的取消交互仍需验收。

P5 采用 `rmcp` 本地 stdio 客户端与 `rquickjs` 后台运行时。服务命令和工具读写白名单由数据目录 `workflow-mcp.json5` 管理；模板只声明服务/工具，运行前展示本次能力并单次授权。同一运行内复用服务连接，运行结束关闭；工具调用前读取实际 schema 并校验参数，不自动重试。JS 只获得已声明工具的 `mcp.call` 桥接，外部任务使用独立线程池。网络 MCP 传输、客户端代理继承、持久授权和 AI Skill 不在本阶段交付范围；真实窗口的键盘、焦点、窄窗及 DPI 验收仍需完成。

## 3. 详细任务与接口检查点

### P1 模板来源

1. 点击“下载模板”后读取固定 CNB 目录，只展示其中的 `.json5/.jsonc` 文件；用户逐个选择下载。
2. 下载前校验文件名和内容，写入普通模板目录。同名文件保持原样，提示“已存在”。
3. 旧版 `remote-cnb` 文件仅导入一次；模板列表只扫描普通目录，删除后刷新不能再从旧目录重复出现。
4. 验证空目录、同名模板、离线、代理错误、损坏 JSON5 和目录穿越的行为。

### P2 来源分支

1. 定义 `WorkflowLaunchContext`：仓库 ID、路径、分支种类、规范化引用、模板 ID、启动代际；写入当前 `RepoTabState.workflow_state`。
2. 菜单项直接使用 `BranchContextMenu` 保存的分支与类型。菜单高度和键盘导航同步更新；模板未加载时允许从已下载/本地列表选择。
3. `WorkflowRunOptions` 增加冻结的来源引用。输入默认值解析、预览和实际运行共用此值；正常入口省略时按原 HEAD 取值。v2 暴露 `run.sourceBranch`。
4. 运行前重新校验仓库与引用；切标签页或模板后清理旧启动上下文。刷新模板和编辑表单不能意外清除当前合法上下文。
5. 重点回归：右键非 HEAD 分支；远端分支；右键后切仓库；加载失败；模板默认输入被用户手动改写；预览后分支被删除或更新。

### P4–P6 执行扩展

1. 先抽出与 UI 无关的 `WorkflowPlan` 和 `StepExecutor`，保留旧 v1 路径适配；每种步骤声明预览、执行、输出、权限和幂等性。
2. 为每次运行生成唯一身份，并在 `WorkflowProgress/Finished/Failed/Cancelled` 中携带；事件收尾校验仓库、运行 ID 与定义摘要。
3. MCP 先实现连接配置、握手、工具列表与 schema 检查，再接直接调用步骤。MCP 服务失败和工具业务失败分开报告；非幂等工具不自动重试。
4. JS 技术验证比较后台引擎与升级 Shell 的兼容、线程限制、Windows release 打包和资源占用；仅在验证后选型。宿主 API 只暴露已授权的动作/MCP 调用，不透传任意命令执行。
5. Skill 包先实现本地显式安装、清单校验和资源读取；AI 运行器复用既有供应商与任务生命周期，设置轮次、token、工具次数与总时长上限。
6. Edge 样板固定页面识别与元素定位策略，验证导航、读取、填写，不触发提交；不得用 GPUI Shell 的 `window` 代替浏览器连接。
